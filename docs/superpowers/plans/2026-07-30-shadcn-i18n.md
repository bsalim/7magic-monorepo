# shadcn/bits-ui Standardization & Dual-Language Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Standardize both SvelteKit apps on shadcn-svelte + bits-ui while preserving the 7magic brand look, then make venue content, articles, and static copy available in Indonesian (default) and English.

**Architecture:** Per-app shadcn installs — `apps/web` gets its own `components.json` and a theme whose tokens carry the existing brand palette, so pages look unchanged while being built from shared primitives. Dual-language uses translation tables (`venue_translations`, plus `locale` + `translation_group_id` on `articles`) with Indonesian as the canonical fallback, exposed through a `?locale=` API parameter and consumed by Paraglide JS on the web with English under an `/en` URL prefix.

**Tech Stack:** SvelteKit 2 + Svelte 5 (runes), Tailwind v4, shadcn-svelte 1.3, bits-ui 2.18, FastAPI + SQLAlchemy 2 (async) + Alembic, Paraglide JS, pnpm workspaces, pytest.

**Spec:** `docs/superpowers/specs/2026-07-30-shadcn-i18n-design.md`

- [ ] **Step 3: Add locale filtering with fallback**

In `ArticleService.public_articles` and `_published_articles`, accept `locale: str = "id"`. Resolution rule:

- `locale == "id"` → return rows where `Article.locale == "id"`.
- `locale == "en"` → return English rows, plus Indonesian rows whose `translation_group_id` has no English sibling.

Implement the fallback with a NOT EXISTS correlated subquery rather than querying twice and merging in Python. Add this module-level helper to `app/services/articles.py`:

```python
from sqlalchemy import and_, exists, or_, select
from sqlalchemy.orm import aliased


def _locale_filter(locale: str):
    if locale == "id":
        return Article.locale == "id"

    sibling = aliased(Article)
    has_translation = exists(
        select(sibling.id).where(
            sibling.translation_group_id == Article.translation_group_id,
            sibling.locale == locale,
        )
    )
    return or_(Article.locale == locale, and_(Article.locale == "id", ~has_translation))
```

The alias is required — without it the subquery correlates `Article` to itself and matches every row. Apply the filter inside `_published_articles` with `.where(_locale_filter(locale))`.

## Deviations from the spec

Recorded here so the spec and plan do not silently disagree:

1. **Task 14 (public venues → DB) is new.** The spec assumed public venue endpoints already read from the database. They serve `fixtures.VENUES` instead, so venue translations cannot reach the site without this task. It is a prerequisite for Task 16, not optional.
2. **Task 18 is API-only if the CMS has no article screens.** The CMS ships only `login`, `logout`, and `venues` routes. Building an article admin UI is a separate project; the plan exposes the locale fields on the API and stops there.
3. **`category_en` on `article_categories` is dropped.** The spec proposed it, but with no article CMS to edit it and no article-category UI on the web beyond the slug, it would be an unused column. Add it when the article admin exists.
4. **The web theme uses hex, not oklch.** The spec did not specify a color format. Hex keeps the palette byte-identical to what renders today; converting to oklch would introduce rounding drift for no benefit.
